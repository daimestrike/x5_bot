# Релиз v1.3.3

Архив самодостаточный: зависимости внутри (`vendor/`). На сервере не нужны интернет, pip, venv,
Docker и зеркало PyPI. Нужен **Ubuntu с Python 3.10 на x86_64** (Ubuntu 22.04).

## Что нового в 1.3.3

**ИИ настроен под X5 AI-Run** — по документации платформы:

- бот подключается как *клиентская система*: `AI_URL=https://direct-llm.airun.x5.ru/v1`
  (DEV — `https://direct-llm.k8s.airun-dev-13.salt.x5.ru/v1`), а не через `api-copilot.x5.ru` для людей;
- серверу нужен сетевой доступ: группа `airun-app-prod-4` в «Сетевые доступы» Salt X5, по согласованию с ИБ;
- модель — `x5-airun-small` (быстрый режим без рассуждений), варианты `-thinking` не рекомендуются;
- `./start.sh --check-ai` при недоступности модели подсказывает про сетевой доступ.

Запросы к модели проверены на соответствие формату AI-Run (OpenAI API, `Authorization: Bearer`);
код клиента менять не потребовалось. Живой вызов шлюза — только с сервера в контуре X5.

## Что вошло из 1.3.2

- **`vendor/` теперь в репозитории.** Архивы, которые отдаёт GitHub (по тегу и «Code → Download ZIP»),
  собираются из git — в 1.3.1 `vendor/` в них был пустым, и на сервере бот не запускался.
  Теперь любой архив с GitHub — готовая поставка.
- Номер версии виден на сервере: `curl -s localhost:8080/health` и `./start.sh --check`.
- README: как скачать с GitHub и распаковать tar.gz или ZIP на Ubuntu без `unzip`.

Код бота и зависимости — те же, что в 1.3.1.

## Где взять

<https://github.com/daimestrike/x5_bot/archive/refs/tags/v1.3.3.tar.gz> → `x5_bot-1.3.3.tar.gz`
(или `rooms-bot-1.3.3.tar.gz` из вложений релиза — то же без тестов и внутренних документов).

## Установка

```bash
sudo mkdir -p /opt/rooms-bot && sudo chown "$USER" /opt/rooms-bot
tar xzf ~/x5_bot-1.3.3.tar.gz --strip-components=1 -C /opt/rooms-bot
cd /opt/rooms-bot && ls vendor | head -3 && ./setup.sh && ./start.sh
sudo ./deploy/install-service.sh     # чтобы работал как служба
```

Открыть со своего компьютера: `ssh -L 8080:127.0.0.1:8080 ПОЛЬЗОВАТЕЛЬ@СЕРВЕР`, затем
<http://127.0.0.1:8080/dev/chat>.

## Включить ИИ

В `.env`: `AI_ENABLED=true`, `AI_URL=https://direct-llm.airun.x5.ru/v1`, `AI_MODEL=x5-airun-small`, `AI_API_KEY` — либо строки `LLM_URL`,
`LLM_MODEL`, `LLM_API_KEY` из `.env` innolib, бот понимает их как есть. Проверить: `./start.sh --check-ai`.

## Обновление с 1.3.0–1.3.2

```bash
cd /opt/rooms-bot && ./update.sh ~/x5_bot-1.3.3.tar.gz --service rooms-bot
```

`.env`, журнал и содержание сохраняются. Проверить, что встала новая версия:
`curl -s localhost:8080/health` → `"version": "1.3.3"`.

## Изменения 1.3.1 (входят в этот релиз)

Проверка на настоящем CPython 3.10 с «голым» окружением выявила и закрыла:

- **`setup.sh` падал на сервере без PyYAML** — проверка содержания шла отдельным процессом без
  `vendor/`. Теперь `vendor/` подключается в одном месте ([app/_bootstrap.py](../app/_bootstrap.py)) при
  любом входе в проект, и только если собран под текущие Python/ОС/архитектуру; иначе — понятная ошибка.
- **systemd-служба не стартовала** — юнит ссылался на несуществующий `.venv`. Теперь
  `sudo ./deploy/install-service.sh` сам подставляет каталог, пользователя и `python3`, проверяет
  конфигурацию от имени службы и запускает её.
- **`update.sh` пропускал проверку конфигурации** при поставке с `vendor/` — теперь проверяет всегда.
- **Откат не возвращал прежние зависимости** — старый `vendor/` теперь переносится в резервную копию
  и возвращается при откате.
- Служебные файлы macOS (`._*`, `.DS_Store`) из перепакованного архива не попадают в установку.

ИИ — под шлюз моделей X5, как в innolib:

- переменные innolib (`LLM_*`, `EMBED_*`) понимаются как есть;
- «рассуждения» Qwen3 отключаются (`AI_DISABLE_THINKING=true`), шлюз без этого параметра
  переспрашивается без него;
- **рассуждения, оборванные лимитом токенов, больше не могут попасть в чат** — раньше обрезанный
  блок `<think>` ушёл бы Аватару вместо ответа;
- `./start.sh --check-ai` — проверка связи с моделью с сервера с подсказками по ошибкам;
- `AI_AUTH_HEADER` — для шлюзов, которые ждут ключ не в `Authorization: Bearer`;
- сбои модели видны в `journalctl`.

Версии зависимостей зафиксированы в `requirements.lock`.

## Что проверено

- 135 тестов на Python 3.9 и **на CPython 3.10 с ровно поставочными версиями** (FastAPI 0.142,
  Starlette 1.7, uvicorn 0.54, Pydantic 2.13).
- Сквозной сценарий сервера на голом Python 3.10: распаковка → `setup.sh` (без `.venv`) → `start.sh` →
  все страницы и экраны диалога → ИИ-ответ со ссылками на карточки → обновление с сохранением
  `.env`, журнала и правок содержания → откат при битой версии с возвратом кода и `vendor/`.
- Шлюз моделей — на эмуляторе с поведением Qwen3: рассуждения, обрыв по лимиту, строгий шлюз,
  неверный ключ, имена переменных innolib.

**Не проверено:** запуск именно на Linux (на машине сборки нет Linux и Docker — сквозной сценарий шёл
на macOS с `vendor/`, собранным из того же `requirements.lock`), `install-service.sh` (нужен systemd)
и настоящий шлюз моделей X5. Первый запуск на сервере: `./start.sh --check` и `./start.sh --check-ai`.
