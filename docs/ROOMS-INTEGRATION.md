## Страница wiki «Под капотом у ROOMS bot-а» (DPP, IMG_2474–2478)

Описывает существующий отправщик алертов из Airflow (`config.py` / `auth.py` / `shablony.py` / `postman.py`).
Подтверждённый исходящий контракт:

| Шаг | Запрос | Что подтверждено | Чего нет на странице |
|---|---|---|---|
| 1. Keycloak | `POST KC_URL`, `client_id` + `client_secret` → `access_token` | стандартный client_credentials | сам адрес `KC_URL`, realm |
| 2. Bot-токен | `GET TOKEN_URL?signature=…` с токеном Keycloak → `result` | `signature` = HMAC от `BOT_ID` и `BOT_SECRET` — совпадает с BotX `/api/v2/botx/bots/{id}/token` | адрес `TOKEN_URL`, имя заголовка для Keycloak-токена |
| 3. Отправка | `POST SEND_URL` `{"group_chat_id", "notification": {"status": "ok", "body", "mentions"}}` | формат = BotX notification, оба токена «в заголовках» | адрес `SEND_URL`, имена заголовков, формат ответа |
| Прочее | `VERIFY_SSL` отключён; ошибки API уходят в `DEBUG_CHAT_ID`; `USER_MAP` логин→huid | — | входящие события (текст, кнопки) — страница только про исходящие уведомления |

В адаптере это реализовано как необязательный слой: `ROOMS_KC_URL`, `ROOMS_KC_CLIENT_ID/SECRET`, `ROOMS_KC_HEADER`,
`ROOMS_TOKEN_URL`, `ROOMS_SEND_URL`, `ROOMS_VERIFY_TLS`. При пустом `ROOMS_KC_URL` — чистый BotX v4.
Секреты из Airflow Variable `Rooms_EDW_DH_BOT` (`bot_id`, `bot_secret`, `kc_client_id`, `kc_client_secret`) в Git не
переносятся — только имена переменных окружения. Для нашего бота нужны **свои** `bot_id`/`bot_secret`, а не ключи DMP.

Открытым остаётся вход: как Chat-Bot Platform доставляет боту сообщения Аватара и нажатия кнопок
(`POST /command` по BotX или иной callback шлюза) и как регистрируется backend URL.

## Текущая реализация

Адаптер `app/transports/rooms.py` реализует **прямой eXpress BotX v4** по документации производителя:

- [Bot API и подпись входящих запросов](https://docs.express.ms/chatbots/developer-guide/api/bot-api/)
- [Команды](https://docs.express.ms/chatbots/developer-guide/api/bot-api/command/)
- [Статус и меню команд](https://docs.express.ms/chatbots/developer-guide/api/bot-api/status/)
- [Получение Bot-токена](https://docs.express.ms/chatbots/developer-guide/api/botx-api/bots-api/)
- [Отправка сообщений и штатные кнопки](https://docs.express.ms/chatbots/developer-guide/api/botx-api/notifications-api/)

Это обоснованная основа интерфейса, но она не доказывает разрешённость прямого подключения в X5. **Авторизация через Keycloak-шлюз X5 реализована по схеме со страницы wiki** (см. выше); не подтверждены адреса и имя
заголовка Keycloak-токена — они задаются переменными окружения. `ROOMS_CONTRACT_CONFIRMED=false` не даёт случайно запустить это как подтверждённую интеграцию.

## Что получить у команды Rooms

Можно передать этот запрос администратору вручную:

> Подключаем бота-справочник для Аватара: личный чат, текст, встроенные кнопки, без ИИ, файлов и рассылок. Просим определить разрешённый маршрут: прямой BotX v4 или корпоративный шлюз. Нужны пример входящего текстового сообщения и нажатия кнопки с описанием проверки подписи; порядок регистрации callback URL; значения `KC_URL`, `TOKEN_URL`, `SEND_URL` и в каком заголовке передаётся Keycloak-токен (бот-токен — `Authorization: Bearer`?); примеры успешного ответа и подтверждения доставки. Для кода DMP достаточно обезличенных функций из auth.py и postman.py с удалёнными значениями секретов. Поддерживает ли шлюз синхронный `/api/v4/botx/notifications/direct/sync` и штатные bubble/keyboard?

Секреты из Vault не вставляйте в документацию или Git. Нам нужны схема запросов и назначения параметров. Действующие ключи затем устанавливаются в секреты окружения сервера.

## Если администратор разрешает прямой BotX

1. Зарегистрировать бот, указать backend URL и Bot API protocol 4, включить личные чаты и необходимые события. Пользователь видит контакт бота в Rooms.
2. Выдать отдельные Bot ID / Secret key. Настроить `ROOMS_API_BASE_URL` как HTTPS origin CTS без пути/слеша в конце; `ROOMS_ISSUER` как точный issuer JWT. Ни один адрес из входящей команды не используется для исходящего запроса.
3. Внести секреты в окружение, настроить CA и двусторонний сетевой доступ. Входящий трафик разрешить только от доверенного BotX/шлюза; обеспечить TLS и синхронизацию времени.
4. Проверить доступность `/direct/sync` в установленной версии. Callback асинхронного `/direct` текущий адаптер не использует для подтверждения; механическая замена адреса отправки недопустима.
5. Согласовать контент и телефонный сценарий, пройти `validate_content.py --production`, отключить `ENABLE_DEV_CONSOLE`, задать `BOT_MODE=production` и только после проверки контракта — `ROOMS_CONTRACT_CONFIRMED=true`.
6. Запустить одну реплику сервиса с постоянным диском. Проверить `/status`, `/menu`, переходы по карточкам, поиск, обе оценки, три причины и помощь на реальном устройстве.
7. Проверить перезапуск с очередью, временный отказ API, истечение токенов, отказ неверной подписи, сетевые ограничения и отсутствие исходных сообщений в логах.

Запросы ограничены 16 КиБ. Используйте события с метаданными файлов (`async_files`), а не встроенные base64-вложения; большие тела отклоняются до разбора. Бот не обрабатывает файл в обоих случаях.

Если X5 требует Keycloak-шлюз, сначала дорабатывается транспорт по его полному контракту и повторяются интеграционные тесты. Текущие тесты с MockTransport подтверждают реализацию документированного протокола, а не работу внутри X5.
