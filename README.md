# Справочник Аватара — бот для чата Rooms

Аватар (директор магазина на удалённой инвентаризации) открывает чат с ботом в Rooms и за три нажатия
получает короткую инструкцию: **Меню → раздел → тема → шаги → Помогло / Не помогло**. Вопрос можно
написать и фразой — тогда отвечает **ИИ по базе знаний** со ссылками на карточки (включается в `.env`).

**Релиз 1.3.2.** Архив самодостаточный: зависимости лежат внутри (`vendor/`), на сервере не нужны
интернет, pip, venv, Docker и зеркало PyPI. Логика — по «MVP бота Rooms.docx» и «Чек-листы_бота_Rooms.xlsx»
([docs/SOURCE-BASELINE.md](docs/SOURCE-BASELINE.md)). Подключение к самому Rooms ждёт контракта
от администратора — что именно нужно, в [docs/ROOMS-INTEGRATION.md](docs/ROOMS-INTEGRATION.md).
До этого бот работает в веб-консоли: её можно показывать и пилотировать.

## 1. Развернуть на сервере

**Нужно:** Ubuntu, **Python 3.10, x86_64** (Ubuntu 22.04 — ровно это). Больше ничего.
Проверить: `python3 -V` → `Python 3.10.x`, `uname -m` → `x86_64`.

**Где взять архив.** На машине с интернетом скачайте с GitHub версию по тегу — в ней уже есть
`vendor/` со всеми зависимостями:

<https://github.com/daimestrike/x5_bot/archive/refs/tags/v1.3.2.tar.gz>  → файл `x5_bot-1.3.2.tar.gz`

```bash
scp x5_bot-1.3.2.tar.gz ПОЛЬЗОВАТЕЛЬ@СЕРВЕР:~/

# на сервере
sudo mkdir -p /opt/rooms-bot && sudo chown "$USER" /opt/rooms-bot
tar xzf ~/x5_bot-1.3.2.tar.gz --strip-components=1 -C /opt/rooms-bot
cd /opt/rooms-bot
ls vendor | head -3   # должно быть не пусто: annotated_doc, annotated_types, anyio…
./setup.sh            # создаёт .env и проверяет конфигурацию; ничего не скачивает
./start.sh            # бот запущен, Ctrl+C — остановить
```

<details>
<summary>Скачали ZIP («Code → Download ZIP»), а не tar.gz</summary>

В ZIP то же самое, `vendor/` внутри. На Ubuntu может не быть `unzip` — распакуйте средствами Python:

```bash
cd /opt/rooms-bot
python3 -m zipfile -e ~/x5_bot-main.zip . && cp -r x5_bot-main/. . && rm -rf x5_bot-main
sh setup.sh && sh start.sh        # через sh: распаковка Python не сохраняет права на запуск
```
</details>

Архив `rooms-bot-1.3.2.tar.gz` из релиза — то же самое, только без тестовых и внутренних документов.

`setup.sh` должен закончиться строками `Конфигурация корректна: mode=demo, cards=35` и `Готово`.

### Открыть в браузере

Бот слушает `127.0.0.1:8080` — снаружи сервера его не видно. Со своего компьютера проще всего через
SSH-туннель:

```bash
ssh -L 8080:127.0.0.1:8080 ПОЛЬЗОВАТЕЛЬ@СЕРВЕР
```

и открыть у себя:

| Страница | Адрес | Ключ |
|---|---|---|
| Диалог (как увидит Аватар) | <http://127.0.0.1:8080/dev/chat> | подставлен сам |
| Метрики пилота | <http://127.0.0.1:8080/metrics/dashboard> | подставлен сам |
| Содержание и ИИ | <http://127.0.0.1:8080/content/> | подставлен сам |

Ключи в демо-режиме — публичные `demo-*` из `.env.example`. Открыть порт всем: `./start.sh --host 0.0.0.0`
— только если сеть закрыта и это осознанно: с демо-ключами страницы доступны любому, кто знает адрес.

### Чтобы бот работал сам, после перезагрузки

```bash
sudo ./deploy/install-service.sh            # служба rooms-bot от вашего пользователя
```

Скрипт подставит каталог, пользователя и `python3`, проверит конфигурацию от имени службы, включит и
запустит её. Дальше: `sudo systemctl status rooms-bot`, логи — `sudo journalctl -u rooms-bot -f`.

## 2. Включить ИИ

ИИ выключен по умолчанию — бот отвечает строго по меню. Модель — платформа **X5 AI-Run**: она
полностью совместима с OpenAI API (`/v1/chat/completions`, ключ в `Authorization: Bearer …`), так же
подключён ИИ в [innolib](https://github.com/daimestrike/innolib). Модели развёрнуты во внутреннем контуре
X5, поэтому для них разрешены коммерческая тайна и персональные данные.

**Что нужно до включения.** Бот — это *клиентская система*, а не пользователь, поэтому ходит не на
`api-copilot.x5.ru` (он для людей), а на прямой адрес для систем:

| Контур | Адрес (`AI_URL`) |
|---|---|
| PROD | `https://direct-llm.airun.x5.ru/v1` |
| DEV | `https://direct-llm.k8s.airun-dev-13.salt.x5.ru/v1` |

1. **Сетевой доступ**: серверу бота добавить группу `airun-app-prod-4` в разделе «Сетевые доступы»
   системы Salt X5. Требует согласования с ИБ — без него `--check-ai` скажет «сервер модели недоступен».
2. **Ключ API** для системы.
3. **Модель** — `x5-airun-small` (Qwen 3.6 35B, быстрый режим без рассуждений). Варианты с `-thinking`
   не берите: медленно, а ответ нужен, пока Аватар держит телефон. Если качества не хватит — `x5-airun-large`.
   Список доступных именно вашему ключу: `curl -s -H "Authorization: Bearer КЛЮЧ" https://direct-llm.airun.x5.ru/v1/models`.

**Если innolib у вас уже работает** — возьмите эти три строки из его `.env` как есть, бот понимает имена
innolib (`LLM_URL`, `LLM_MODEL`, `LLM_CHAT_MODEL`, `LLM_API_KEY`, `LLM_CA_BUNDLE`, `LLM_EXTRA_JSON`…):

```ini
AI_ENABLED=true
LLM_URL=https://адрес-шлюза/v1
LLM_MODEL=имя-модели
LLM_API_KEY=ключ
```

**Или своими именами** — в `/opt/rooms-bot/.env`:

```ini
AI_ENABLED=true
AI_URL=https://direct-llm.airun.x5.ru/v1    # с /v1 на конце; DEV — адрес из таблицы выше
AI_MODEL=x5-airun-small
AI_API_KEY=ключ
```

Проверьте связь **до** перезапуска — команда скажет, что не так:

```bash
cd /opt/rooms-bot && ./start.sh --check-ai
```

```
Модель: x5-airun-small  адрес: https://direct-llm.airun.x5.ru/v1  ключ: задан
Модели на сервере: x5-airun-small, x5-airun-small-thinking, x5-airun-large, …
Тестовый ответ модели: Готов
Время ответа: 1.4 с
Рассуждения отключены (enable_thinking=false) — шлюз параметр принял.
База знаний: 35 фрагментов (карточки и загруженные документы)
Связь с моделью есть — ИИ-ответы в боте работают.
```

Затем перезапустите бота (`sudo systemctl restart rooms-bot` или `Ctrl+C` и `./start.sh`) и напишите в
диалоге фразой: «что делать если пропала связь в магазине». Состояние ИИ видно и на вкладке **ИИ**
страницы `/content/`, сбои — в `sudo journalctl -u rooms-bot`.

**Про модели Qwen3 в шлюзе X5.** Они по умолчанию «рассуждают» (`<think>…</think>`): отвечают в разы
дольше и могут израсходовать весь лимит токенов на рассуждения. Бот, как и innolib, отключает это
параметром `chat_template_kwargs.enable_thinking=false` (`AI_DISABLE_THINKING=true` по умолчанию).
Если шлюз такой параметр не знает — бот повторяет запрос без него. Рассуждения в ответе вырезаются
всегда, в том числе оборванные лимитом: в чат Аватару они не попадут.

| Что ответил `--check-ai` | Что поправить |
|---|---|
| `ключ не подошёл` (HTTP 401/403) | `AI_API_KEY`; если ключ верный — `AI_AUTH_HEADER` (`api-key`, `X-API-Key`) |
| `адрес или имя модели неверны` (404) | `AI_URL` должен оканчиваться на `/v1`; `AI_MODEL` — из строки «Модели на сервере» |
| `сервер модели недоступен` | нет сетевого доступа: группа `airun-app-prod-4` в Salt X5; адрес; прокси — `AI_USE_SYSTEM_PROXY=true`; внутренний сертификат — `AI_CA_FILE=/путь/к/ca.pem` |
| `модель ушла в рассуждения` | `AI_DISABLE_THINKING=true`; либо `AI_MAX_TOKENS=1500` |
| `Время ответа: 20 с — долго` | `x5-airun-small` без `-thinking`; проверьте статус моделей на странице AI-Run «Отслеживание статуса моделей» |
| `ИИ выключен` | `AI_ENABLED=true` |

Если модель недоступна во время работы, бот не ломается — отвечает как без ИИ, по меню. Что уходит
в модель и какие у ответа границы — в разделе [«ИИ-ответ по базе знаний»](#ии-ответ-по-базе-знаний-rag).

## 3. Обновить на новую версию

```bash
scp rooms-bot-НОВАЯ.tar.gz* ПОЛЬЗОВАТЕЛЬ@СЕРВЕР:~/
cd /opt/rooms-bot && ./update.sh ~/rooms-bot-НОВАЯ.tar.gz --service rooms-bot
```

Подойдёт любой архив новой версии: tar.gz или zip с GitHub либо `rooms-bot-*.tar.gz` из релиза.
`update.sh` сверяет контрольную сумму (если рядом лежит `.sha256`) → делает резервную копию → меняет код и `vendor/` → проверяет
конфигурацию → перезапускает службу. **Не трогает** `.env`, журнал `data/` и содержание `content/`
(карточки, загруженные документы, очередь проверки). Если новая версия не прошла проверку —
сам возвращает прежний код и зависимости. Без службы — уберите `--service rooms-bot` и запустите
`./start.sh`.

Откатиться вручную на предыдущую версию:

```bash
ls backups/                                         # pre-update-ГГГГММДД-ЧЧММСС
cp -r backups/pre-update-ПОСЛЕДНЯЯ/code/. . && sudo systemctl restart rooms-bot
```

## 4. Если что-то не так

| Сообщение | Причина и решение |
|---|---|
| `Нужен 64-разрядный Python 3.10 или новее` | на сервере старый Python — нужен 3.10 |
| `vendor/ собран под Python 3.10 linux x86_64, а запущен …` | другой Python или ARM. На машине с интернетом: `python scripts/vendor.py --python-version 3.X --arch x86_64\|aarch64`, затем `python scripts/package.py --name rooms-bot-1.3.2` |
| `Нет .env` | выполните `./setup.sh` |
| `Зависимости не найдены: каталога vendor/ нет` | скачан архив без `vendor/` (версия до 1.3.2 или ветка без него) — возьмите tar.gz по тегу v1.3.2 и новее |
| `Permission denied` на `./setup.sh` | распаковали ZIP средствами Python — запускайте `sh setup.sh`, `sh start.sh` |
| `Address already in use` | порт занят: `PORT=8081` в `.env` или остановите прежний процесс |
| `Конфигурация … ошибка` в `update.sh` | обновление отменено само, прежняя версия работает; пришлите текст ошибки |
| служба не стартует | `sudo journalctl -u rooms-bot -n 50 --no-pager` |

Проверки одной строкой:

```bash
./start.sh --check                    # конфигурация и содержание
./start.sh --check-ai                 # связь с моделью ИИ
curl -s localhost:8080/health         # сервис жив, какая версия, ИИ включён?
```

## Как выглядит диалог

- Приветствие один раз за сеанс, кнопка «Меню».
- Пять разделов по MVP, «Поиск» и «Помощь человека».
- Не больше восьми тем на странице; любая карточка — максимум три нажатия от меню.
- В карточке заголовок, до шести шагов, ссылка, «Помогло», «Не помогло», «Другие темы», «Меню».
- После «Не помогло» — три причины из чек-листа и ссылка на инструкцию.
- Поиск по одному-двум словам, до пяти результатов.
- Вопрос фразой: без ИИ — «понимаю только меню»; с ИИ — ответ по базе знаний, коды карточек становятся кнопками.
- Голосовые и файлы не обрабатываются.

Карточки помечены «ЧЕРНОВИК ДЛЯ ПРОВЕРКИ», пока владелец содержания их не утвердил (страница `/content/`).
Кнопки в Rooms отправляются штатными `bubble` и `keyboard` BotX.

## Для разработчика

Сборка релиза (на машине с интернетом):

```bash
python scripts/vendor.py                    # зависимости под Linux x86_64 / Python 3.10 → vendor/
python scripts/vendor.py --verify           # состав и формат двоичных файлов
python scripts/package.py --name rooms-bot-1.3.2 --format tar
```

Версии зафиксированы в `requirements.lock` — повторная сборка даёт тот же набор, что проверен тестами;
обновить осознанно — `--refresh`. `vendor/` подключается автоматически при импорте пакета `app`, но только
если собран под текущие Python, ОС и архитектуру (метка `vendor/VENDOR.json`, код — [app/_bootstrap.py](app/_bootstrap.py)).

Тесты и проверки:

```bash
python -m pip install -r requirements-dev.txt
python -m pytest -q
python -m ruff check app scripts tests
```

Без `vendor/` установщик ставит зависимости в `.venv`: `./setup.sh --index-url https://ВНУТРЕННИЙ-PYPI/simple`
или из собранного `wheels/` — `./setup.sh --offline`. Публичный PyPI намеренно не используется.

Демо-консоль локально — `make demo`; ИИ без настоящей модели — заглушка `scripts/mock_llm.py`
(см. раздел про ИИ). Секреты `demo-*` в production запрещены; настоящие — `python scripts/init_env.py --secure`.

## Контент и согласование

`content/cards.yaml` содержит все 35 исходных **черновиков**. Отсутствующие источники, владельцы и контакты не выдуманы. До рабочего запуска владелец заполняет URL/owner, проверяет тексты, повышает version/date и выставляет `approved: true`, `status: published`.

`content/settings.yaml` содержит разделы, резервную ссылку, разрешённые домены ссылок и подтверждение использования телефона во время ПИ. Чат на ТСД не должен прерывать запись — это нужно проверить на устройстве в контуре.

```sh
python scripts/validate_content.py --production
```

На поставленных черновиках production-проверка **ожидаемо завершается ошибкой**. Обычная валидация проверяет структуру, длину заголовков и ответов, число шагов и синонимов. Наличие флага согласования не заменяет проверку владельцем.

Карточки изменяются через GitLab merge request, после изменения YAML сервис перезапускают. Снятый материал помечается `available: false` и открывает S8. Оценка привязана к версии показанной карточки. Импорт нового Excel:

```sh
python scripts/import_registry.py "Чек-листы_бота_Rooms.xlsx" --out content/cards-import-review.yaml
```

Импорт создаёт новый файл черновиков для редактирования, не перезаписывает рабочую базу и не публикует материалы.

## Сервер и доставка

Входящие методы прямого BotX: `POST /command`, `GET /status`, `POST /notification/callback`. Запросы проверяются по JWT HS256: подпись, issuer, audience, срок действия. Старый предполагаемый `/webhook/rooms` удалён.

Состояние диалога и очередь ответов записываются **одной транзакцией до HTTP 202**. Отдельная задача доставляет сообщения через документированный `/api/v4/botx/notifications/direct/sync`; успешным считается только HTTP 200 с `status: ok` и корректным `sync_id`. Не используйте вместо него асинхронный `/direct`: для него потребуется подтверждение доставки через callback.

Очередь переживает перезапуск. Уже подтверждённые части ответа повторно не отправляются; повтор входящего `sync_id` не создаёт новую выдачу. Между ответами одного чата сохраняется порядок. При ошибке — повтор с задержкой до пяти минут, срок жизни ответа один час. Истечение фиксируется в метриках, адрес доставки удаляется. Дедупликация входящих событий действует 24 часа.

Полная гарантия «ровно один раз» не заявляется: если Rooms принял сообщение, но соединение оборвалось до ответа или процесс завершился до фиксации подтверждения, повтор может создать дубликат. Нужен поддерживаемый шлюзом ключ идемпотентности, чтобы закрыть это окно.

## Содержание: обновление документации без правки кода

Страница `http://<host>:8080/content/` (доступ по `METRICS_TOKEN`, в поле «Кто работает» — ФИО) — три вкладки.

**Источники.** Загрузите текущую версию каждого документа (.docx, .txt, .md; .pdf при наличии `pypdf`).
Бот сохраняет слепок текста по абзацам в `content/sources/<key>.json`, сам файл не хранит. Следующая
загрузка того же ключа сравнивается со слепком: изменённые, добавленные и удалённые абзацы попадают
в очередь с пословной подсветкой «было / стало» и номером фрагмента (для PDF — страницы). Алгоритм
подбирает связанные карточки автоматически, без меток в документе и ручной разметки связей.
Для Word учитываются заголовки (в том числе пользовательские стили на основе заголовков),
разделы, строки и шапки таблиц, соседний текст. Окончания русских слов нормализуются;
редкие термины, название и синонимы карточки имеют больший вес. `source_key` помогает ранжированию.
Связи и постоянные ID фрагментов сохраняются в слепке уже при первой загрузке.
Перенос неизменённого абзаца внутри раздела не создаёт изменения; при переносе в другой раздел
контекст отправляется на проверку. Уверенные связи используются в последующих версиях только
при однозначном сопоставлении фрагмента и неизменившемся определении карточки.
В очереди видны основания выбора и категории «Сильная связь», «Возможная связь», «Несколько кандидатов».
Это эвристический подбор, а не вероятность правильности: неизвестные темы остаются без карточки,
сильно переписанные или неоднозначные фрагменты могут отображаться как удалённые и добавленные.
Нормализация окончаний не является полной морфологией русского языка. Интернет и дополнительные
пакеты для этого алгоритма не нужны. Пользовательский поиск бота остаётся буквальным по MVP.

Слепок обновляется автоматически при повторной загрузке; старые слепки совместимы. Первая загрузка
строит связи, а очередь появляется при изменениях следующей версии. Пересохранение Word с тем же
текстом и структурой (но другими ZIP-метаданными) не увеличивает версию. Сравнение ограничено
1500 фрагментами по 12000 знаков и 8 МБ входного файла. Изображения внутри Word и сканированные PDF
не распознаются: OCR не входит в эту функцию. Для PDF с текстовым слоем по-прежнему нужен `pypdf`.

**Очередь.** По каждому изменению — решение человека: «Текст актуален», «Открыть карточку» (правка),
«Не относится». Ничего не попадает в бот автоматически. Разобранное сохраняется с фамилией и датой.

**Карточки.** Правка создаёт новую версию (`0.1.0 → 0.2.0`, дата, `approved: false`, прошлая версия —
в `history`), утверждение — с фамилией проверяющего. В demo бот перечитывает карточки сразу и помечает
черновики; в production бот продолжает выдавать прежнюю версию, пока все карточки не утверждены.
Оценки в журнале привязаны к версии, поэтому переписывать БД не нужно.

Файлы `content/cards.yaml`, `content/sources/*.json`, `content/review/pending.json` — источник правды;
их стоит коммитить в GitLab после сессии правок. В Docker каталог `content/` смонтирован `:ro` —
для работы страницы «Содержание» на сервере уберите `:ro` или используйте отдельный том.

Ограничение по замыслу MVP: алгоритм **не пишет** текст карточек по документу — он находит место
изменения и не даёт его пропустить. Текст пишет и утверждает человек.

## ИИ-ответ по базе знаний (RAG)

По умолчанию **выключен**: бот работает строго по меню и поиску, как в MVP. При `AI_ENABLED=true`
вопрос, написанный фразой, не упирается в «понимаю только меню», а получает ответ по базе знаний.

**Как устроено.** Вопрос → поиск фрагментов (BM25 с русским стеммингом по карточкам и загруженным
документам) → модели уходит системный промпт + найденные фрагменты + вопрос → ответ со ссылками
на карточки вида `[A-07]`. Коды из ответа превращаются в кнопки: Аватар открывает карточку целиком.
Под ответом — те же «Помогло / Не помогло», оценки попадают в метрики.

| Файл | Назначение |
|---|---|
| [app/llm.py](app/llm.py) | клиент OpenAI-совместимого API на стандартной библиотеке: без новых зависимостей, свой CA, прокси отключён, `<think>` у reasoning-моделей вырезается |
| [app/rag.py](app/rag.py) | индекс базы знаний: BM25 + необязательные эмбеддинги (RRF), промпт, разбор ссылок на карточки |
| [app/assistant.py](app/assistant.py) | связывает поиск и модель, помечает ответ как подтверждённый или нет |

**База знаний ИИ** — те же файлы, что у бота: карточки `content/cards.yaml` (только доступные)
и слепки документов `content/sources/*.json`, которые создаёт страница «Содержание». Отдельной
базы и отдельной загрузки нет: обновили документ — ИИ отвечает по новой версии.

**Границы, заданные промптом и кодом:**

- отвечать только по переданным фрагментам; нет ответа — сказать об этом и предложить меню;
- ссылаться кодами карточек, коды из ответа сверяются с каталогом — выдуманные отбрасываются;
- если не осталось ни одной ссылки, ответ помечается неподтверждённым и к нему добавляется
  строка «проверьте по меню или спросите ревизора»;
- не называть пароли и коды, не вести по этапам ПИ, не выполнять действий в GK/Inventa;
- сбой или таймаут модели не ломает диалог: бот отвечает как раньше, по меню.

**Что уходит в модель:** вопрос Аватара и фрагменты согласованных материалов. Имена, идентификаторы
Rooms и содержание ПИ не отправляются и не записываются — в журнале остаются только факт ответа,
модель, подтверждён он ссылками или нет, и оценка.

**Настройка** — раздел [«2. Включить ИИ»](#2-включить-ии) в начале; полный список параметров —
в `.env.example`. `AI_TIMEOUT` держите меньше таймаута шлюза BotX: ответ считается до подтверждения
сообщения.

Эмбеддинги необязательны. Если задать `AI_EMBED_MODEL`, к BM25 добавляется векторный поиск,
векторы считаются в фоне и кэшируются в `data/embeddings.sqlite3`; при недоступности модели
эмбеддингов поиск продолжает работать на BM25.

Состояние и проверка связи — вкладка **ИИ** на странице `/content/`: модель, адрес, размер индекса,
кнопка «Проверить связь с моделью». То же в `GET /health`.

**Проверить без настоящей модели** — заглушка, которая отвечает тем, что нашёл RAG:

```bash
python scripts/mock_llm.py --port 8011
AI_ENABLED=true AI_URL=http://127.0.0.1:8011/v1 AI_MODEL=mock make demo
```

Это проверка конвейера (поиск → контекст → ответ → ссылки на карточки), а не качества модели.

## Продуктовые метрики

Страница `http://<host>:8080/metrics/dashboard` — дашборд пилота по разделу 8 MVP: сеансы, обращения, охват оценкой
(цель ≥ 50%), полезность (цель ≥ 70%), пробелы базы (карточки с «Не помогло» и причины, промахи
поиска, непонятные фразы), динамика по дням, разбивка по разделам, топ карточек, техника (ошибки выдачи, очередь).
Данные запрашиваются по `METRICS_TOKEN` (вводится на странице; в демо подставляется публичный `demo-*`).
JSON — `GET /metrics/product?days=30` с заголовком `Authorization: Bearer <METRICS_TOKEN>`.

Всё считается по обезличенному журналу. Показатели «на одну ПИ» (использование, отвлечения ревизора,
качество ПИ) в журнале посчитать нельзя — их собирает наблюдатель на пилоте.

**Участники.** В журнале у каждого события есть `participant` — 10-символьный псевдоним (HMAC от id пользователя
Rooms на `BOT_STATE_SECRET`, необратим, одинаков между сеансами). Имена и HUID по-прежнему не хранятся.
Чтобы на дашборде видеть «Магазин 4471, ДМ» вместо псевдонима, владелец пилота вписывает соответствие
в `content/participants.yaml` (`псевдоним: "подпись"`), сопоставив сеанс с ПИ по времени. Псевдоним виден
в блоке «Участники» и в `/metrics/journal.csv`. Так закрывается «ручное сопоставление сеансов с ПИ» из MVP.

Чтобы посмотреть дашборд на тестовых данных: `make seed` (только в demo) генерирует синтетические обращения за 14 дней.

## Данные и эксплуатация

- Аналитика: время UTC, тема, версия, оценка, причина, факт промаха поиска и доставка. Исходных сообщений, имён, прямых ID и содержания ПИ в журнале нет.
- Сеанс: HMAC от пары чат/пользователь, четыре часа бездействия. Кнопка оценки действует четыре часа после показа.
- Операционная очередь: только зашифрованный идентификатор чата; удаляется после доставки или истечения часа. Ключ получен из `BOT_STATE_SECRET`. Ответы в replay-кэше содержат только материалы справочника.
- Поиск без результата сохраняется как `redacted`: запрет MVP на ПДн/содержание ПИ имеет приоритет над предложением Excel записывать свободный текст.
- Аналитика хранится 30 дней. Политика физического удаления SQLite/WAL/резервных копий задаётся инфраструктурой.
- `/metrics/summary` и `/metrics/journal.csv` защищены отдельным `METRICS_TOKEN`; summary включает состояние очереди. `/health` и `/ready` проверяют сервис/БД, не реальную доставку в Rooms.
- Один процесс, одна реплика, локальный постоянный диск. Не размещайте SQLite на общей NFS и не запускайте несколько экземпляров.
- TLS проверяется; внутренний CA задаётся `ROOMS_CA_FILE`. Вложения не скачиваются. HTTP access logs отключены, так как запросы BotX могут содержать атрибуты пользователя.

Экспорт и резервная копия, без перезаписи существующих файлов:

```sh
python scripts/export_journal.py --csv journal.csv
python scripts/backup.py backups/bot.sqlite3
```

Создайте каталог backups заранее. Для восстановления остановите сервис и восстановите БД вместе с соответствующим `BOT_STATE_SECRET`. Смена этого секрета делает старую маршрутизацию нерасшифровываемой. API/metrics-токены можно менять независимо.

## GitLab и закрытый контур

В репозиторий загрузите код, YAML, тесты и `.gitlab-ci.yml`. Не загружайте `.env`, `data/`, фотографии внутренней документации и резервные копии.

CI: внутренний образ `PYTHON_IMAGE`, установка только из `wheels/`, валидация, Ruff, pytest, ZIP-артефакт. Подготовьте Linux wheels для архитектуры и Python целевого сервера, включая транзитивные зависимости. См. [wheels/README.md](wheels/README.md).

Docker — **необязательный** путь: на целевом сервере его может не быть, и всё работает
через `setup.sh` / `start.sh` и systemd-юнит из `deploy/`. Если Docker с compose всё же доступен,
образ собирается без доступа к публичным реестрам пакетов:

```sh
docker compose up --build -d
```

Базовый образ должен уже быть доступен во внутреннем registry. Контейнер работает от UID 10001 с read-only файловой системой и volume для БД. Порт доступен только на loopback; доступ из Rooms настраивается через корпоративный reverse proxy и сетевые правила. Смонтируйте корпоративный CA read-only, если он нужен.

Build/push образа в GitLab включается `BUILD_IMAGE=true` на shell runner с тегом `rooms-docker` и настроенным Docker. Автоматический deploy в X5 отсутствует: инфраструктурные адреса и права не предоставлены.

## Обновление старого проекта

Старые настройки `SEARCH_ENABLED`, `LOG_FREE_TEXT`, `JOURNAL_USER_MODE`, `DEMO_CONSOLE`, `ROOMS_SEND_PATH`, `ROOMS_BOT_TOKEN` заменены новым `.env.example`. Существующую `.env` не переносите вслепую. Новая БД — `data/bot-v2.sqlite3`; старая БД намеренно не мигрируется, поскольку могла содержать исходные сообщения и ID. Хранение старых данных решается отдельно.
