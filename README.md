# Справочник Аватара — бот для чата Rooms

Пользователь работает в личном чате: **Меню → раздел → тема → короткая инструкция → Помогло / Не помогло**. На клавиатуре доступны «Меню» и «Поиск». Отдельный сайт сотруднику не нужен. Сервис запускается на сервере внутри контура; интерфейс сообщений и кнопок отображает сам мессенджер.

Логика приведена к файлам «MVP бота Rooms.docx» и «Чек-листы_бота_Rooms.xlsx»: пять разделов, 35 карточек, буквальный поиск, причины отрицательной оценки и три маршрута помощи. Без ИИ, рассылок, управления этапами ПИ и действий в GK/Inventa.

**Готовы логика, локальные проверки и адаптер прямого eXpress BotX v4. Подключение через шлюз X5 пока не завершено.** На предоставленных фотографиях X5 используются два токена — Keycloak и Bot. Полные URL, HTTP-заголовки и входящие события на снимках отсутствуют. Текущий прямой адаптер нельзя выдавать за проверенную интеграцию с этим шлюзом. Точные недостающие сведения перечислены в [инструкции подключения](docs/ROOMS-INTEGRATION.md).

## Как выглядит диалог

- Приветствие один раз за сеанс, кнопка «Меню».
- Пять разделов по MVP, «Поиск», «Помощь человека».
- Не больше восьми тем на странице; любая карточка — максимум три нажатия от меню.
- В карточке заголовок, до шести шагов, ссылка, «Помогло», «Не помогло», «Другие темы», «Меню».
- После «Не помогло» — три причины из чек-листа и переход к инструкции/помощи.
- Поиск по одному-двум словам, до пяти результатов. Развёрнутые вопросы, голосовые и файлы не обрабатываются.

Кнопки отправляются как штатные `bubble` и `keyboard` BotX, без HTML, внешних страниц и собственного оформления Rooms. Проверочная веб-консоль выключена по умолчанию и недоступна в production.

## Проверка проекта локально

Python **3.12**, зависимости из разрешённого зеркала либо подготовленного wheelhouse:

```sh
python3 -m venv .venv
. .venv/bin/activate
python -m pip install --no-index --find-links=wheels -r requirements-dev.txt
python scripts/init_env.py
python scripts/validate_content.py
python -m pytest -q
python -m ruff check app scripts tests
```

Если `wheels/` ещё не наполнен, установите зависимости через внутренний `PIP_INDEX_URL`, разрешённый в вашей организации. Wheels и базовый Docker-образ в исходный архив не включены.

Необязательный симулятор диалога для разработчика:

```sh
make demo
```

Откройте `http://127.0.0.1:8080/dev/chat`, используйте `BOT_API_TOKEN` из `.env`. `make demo` явно включает консоль только для этого запуска. Это проверка сценария, она не подтверждает подключение к Rooms. Корневой адрес `/` не обслуживает веб-приложение.

## Контент и согласование

`content/cards.yaml` содержит все 35 исходных **черновиков**. Отсутствующие источники, владельцы и контакты не выдуманы. До рабочего запуска владелец заполняет URL/owner, проверяет тексты, повышает version/date и выставляет `approved: true`, `status: published`.

`content/settings.yaml` содержит разделы, три маршрута помощи, резервную ссылку, разрешённые домены ссылок и подтверждение использования телефона во время ПИ. Чат на ТСД не должен прерывать запись — это нужно проверить на устройстве в контуре.

```sh
python scripts/validate_content.py --production
```

На поставленных черновиках production-проверка **ожидаемо завершается ошибкой**. Обычная валидация проверяет структуру, длину заголовков и ответов, число шагов и синонимов. Наличие флага согласования не заменяет проверку владельцем.

Карточки изменяются через GitLab merge request, после изменения YAML сервис перезапускают. Снятый материал помечается `available: false` и открывает S8. Оценка привязана к версии показанной карточки. Импорт нового Excel:

```sh
python scripts/import_registry.py "Чек-листы_бота_Rooms.xlsx" --out content/cards-import-review.yaml
```

Импорт создаёт новый файл черновиков для редактирования, не перезаписывает рабочую базу и не публикует материалы.

## Сервер и доставка

Входящие методы прямого BotX: `POST /command`, `GET /status`, `POST /notification/callback`. Запросы проверяются по JWT HS256: подпись, issuer, audience, срок действия. Старый предполагаемый `/webhook/rooms` удалён.

Состояние диалога и очередь ответов записываются **одной транзакцией до HTTP 202**. Отдельная задача доставляет сообщения через документированный `/api/v4/botx/notifications/direct/sync`; успешным считается только HTTP 200 с `status: ok` и корректным `sync_id`. Не используйте вместо него асинхронный `/direct`: для него потребуется подтверждение доставки через callback.

Очередь переживает перезапуск. Уже подтверждённые части ответа повторно не отправляются; повтор входящего `sync_id` не создаёт новую выдачу. Между ответами одного чата сохраняется порядок. При ошибке — повтор с задержкой до пяти минут, срок жизни ответа один час. Истечение фиксируется в метриках, адрес доставки удаляется. Дедупликация входящих событий действует 24 часа.

Полная гарантия «ровно один раз» не заявляется: если Rooms принял сообщение, но соединение оборвалось до ответа или процесс завершился до фиксации подтверждения, повтор может создать дубликат. Нужен поддерживаемый шлюзом ключ идемпотентности, чтобы закрыть это окно.

## Данные и эксплуатация

- Аналитика: время UTC, тема, версия, оценка, причина, тип помощи, факт промаха поиска и доставка. Исходных сообщений, имён, прямых ID и содержания ПИ в журнале нет.
- Сеанс: HMAC от пары чат/пользователь, четыре часа бездействия. Кнопка оценки действует четыре часа после показа.
- Операционная очередь: только зашифрованный идентификатор чата; удаляется после доставки или истечения часа. Ключ получен из `BOT_STATE_SECRET`. Ответы в replay-кэше содержат только материалы справочника.
- Поиск без результата сохраняется как `redacted`: запрет MVP на ПДн/содержание ПИ имеет приоритет над предложением Excel записывать свободный текст.
- Аналитика хранится 30 дней. Политика физического удаления SQLite/WAL/резервных копий задаётся инфраструктурой.
- `/metrics/summary` и `/metrics/journal.csv` защищены отдельным `METRICS_TOKEN`; summary включает состояние очереди. `/health` и `/ready` проверяют сервис/БД, не реальную доставку в Rooms.
- Один процесс, одна реплика, локальный постоянный диск. Не размещайте SQLite на общей NFS и не запускайте несколько экземпляров.
- TLS проверяется; внутренний CA задаётся `ROOMS_CA_FILE`. Вложения не скачиваются. HTTP access logs отключены, так как запросы BotX могут содержать атрибуты пользователя.

Экспорт и резервная копия, без перезаписи существующих файлов:

```sh
python scripts/export_journal.py --csv journal.csv
python scripts/backup.py backups/bot.sqlite3
```

Создайте каталог backups заранее. Для восстановления остановите сервис и восстановите БД вместе с соответствующим `BOT_STATE_SECRET`. Смена этого секрета делает старую маршрутизацию нерасшифровываемой. API/metrics-токены можно менять независимо.

## GitLab и закрытый контур

В репозиторий загрузите код, YAML, тесты и `.gitlab-ci.yml`. Не загружайте `.env`, `data/`, фотографии внутренней документации и резервные копии.

CI: внутренний образ `PYTHON_IMAGE`, установка только из `wheels/`, валидация, Ruff, pytest, ZIP-артефакт. Подготовьте Linux wheels для архитектуры и Python целевого сервера, включая транзитивные зависимости. См. [wheels/README.md](wheels/README.md).

Docker собирается без доступа к публичным реестрам пакетов:

```sh
docker compose up --build -d
```

Базовый образ должен уже быть доступен во внутреннем registry. Контейнер работает от UID 10001 с read-only файловой системой и volume для БД. Порт доступен только на loopback; доступ из Rooms настраивается через корпоративный reverse proxy и сетевые правила. Смонтируйте корпоративный CA read-only, если он нужен.

Build/push образа в GitLab включается `BUILD_IMAGE=true` на shell runner с тегом `rooms-docker` и настроенным Docker. Автоматический deploy в X5 отсутствует: инфраструктурные адреса и права не предоставлены.

## Обновление старого проекта

Старые настройки `SEARCH_ENABLED`, `LOG_FREE_TEXT`, `JOURNAL_USER_MODE`, `DEMO_CONSOLE`, `ROOMS_SEND_PATH`, `ROOMS_BOT_TOKEN` заменены новым `.env.example`. Существующую `.env` не переносите вслепую. Новая БД — `data/bot-v2.sqlite3`; старая БД намеренно не мигрируется, поскольку могла содержать исходные сообщения и ID. Хранение старых данных решается отдельно.

Соответствие требованиям: [ACCEPTANCE.md](docs/ACCEPTANCE.md). Проверки и ограничения: [VALIDATION.md](docs/VALIDATION.md).
