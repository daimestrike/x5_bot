# Справочный бот Аватара в Rooms (MVP v11)

Помощник Аватара при удалённой ПИ: меню → раздел (типовые вопросы / инструкции / чек-листы / нужна помощь)
→ тема → материал, оценка «Помогло / Не помогло», контакт для помощи и журнал обращений.
Без ИИ, без рассылок, без интеграций с Inventa/GK — по бизнес-требованиям «MVP бота Rooms, версия 11»
и файлу «Чек-листы_бота_Rooms_v11.xlsx».

Стартовая база — 35 текстов из реестра v9, переложенных в формат карточки v11 (тип, когда применять,
что подготовить, действия, ожидаемый результат, к кому обратиться, источник, ответственный, проверяющий,
версия, дата проверки, статус). Поля «когда / результат / если не получается» заполнены по смыслу текста —
их должен подтвердить проверяющий; в v11 реестр пуст (шаблон), готовых текстов там нет.

## Что внутри

```
app/
  engine.py          диалог: меню, разделы, темы, оценки, помощь, свободный текст (лист «Логика ответов»)
  content.py         загрузка и проверка карточек v11, статусы и версии (листы «Карточка», «Подготовка чек-листов»)
  search.py          поиск по словам — за флагом SEARCH_ENABLED (в v11 выключен)
  journal.py         журнал обращений в SQLite: тема, время, версия, оценка, помощь, участник, сеанс
  metrics.py         сводка по листу «Метрики» + таблица обращений для привязки к ПИ
  sessions.py        сеансы пользователей (приветствие S0 — один раз за сеанс)
  main.py            HTTP: webhook Rooms, демо-консоль, метрики, health
  transports/rooms.py адаптер Bot API Rooms — единственное место, зависящее от мессенджера
  static/index.html  демо-консоль для приёмки (открывается на /)
content/
  cards.yaml         материалы (формат карточки v11) — правит ответственный за содержание, без разработчика
  screens.yaml       тексты и подписи кнопок экранов
  help_routes.yaml   «Нужна помощь»: порядок обращения и контакты (заполнить!)
  params.yaml        ссылки на документы, имя сети — изменяемые параметры
scripts/
  import_registry.py импорт из xlsx: листы-карточки v11 (шаблон «Карточка чек-листа») или реестр v9
  validate_content.py проверка содержания (длина, пункты, результат у чек-листа, статусы, версии, секреты)
  export_journal.py  выгрузка журнала в CSV + сводка метрик
tests/               45 тестов: лист «Приёмка MVP» v11, «Логика ответов», импорт
```

## Быстрый старт (локально)

```bash
python3 -m venv .venv && . .venv/bin/activate
pip install -r requirements-dev.txt
cp .env.example .env
python scripts/validate_content.py
python -m pytest -q
uvicorn app.main:app --port 8080
```

Откройте http://localhost:8080 — демо-консоль. Она ходит в тот же движок, что и Rooms,
поэтому по ней можно пройти весь лист «Приёмка MVP» до подключения мессенджера.

## Docker

```bash
cp .env.example .env   # заполнить ROOMS_* и JOURNAL_SALT
docker compose up --build -d
curl localhost:8080/health
```

Каталог `content/` монтируется в контейнер только для чтения: правка карточки = правка YAML +
`docker compose restart bot`. Пересборка образа не нужна. Журнал лежит в `./data/journal.sqlite3`.

В закрытом контуре задайте `PIP_INDEX_URL` (зеркало PyPI в Artifactory) — он передаётся
в `docker build` и в CI.

## Подключение к Rooms

Бот работает по схеме webhook: Rooms присылает событие на `POST /webhook/rooms`,
бот отвечает через Bot API Rooms (`ROOMS_API_BASE_URL` + `ROOMS_SEND_PATH`, токен `ROOMS_BOT_TOKEN`).

Публичной документации на Bot API Rooms нет, поэтому формат зафиксирован в одном файле —
[app/transports/rooms.py](app/transports/rooms.py) — и при подключении к контуру нужно сверить с документацией
команды Rooms две функции:

| Функция | Что уточнить |
|---|---|
| `parse_update(payload)` | имена полей: id пользователя и чата, текст, данные нажатой кнопки, вложения. Сейчас понимает распространённые варианты (`user_id`/`from.id`, `chat_id`/`chat.id`, `text`, `callback_data`, `callback_query`) |
| `build_payload(...)` | тело запроса на отправку: сейчас `{"chat_id", "text", "buttons": [[{"text","callback_data"}]]}` |

Если Rooms не поддерживает inline-кнопки — поставьте `ROOMS_BUTTONS_MODE=text`: кнопки печатаются
нумерованным списком, Аватар отвечает номером («2») или подписью («Меню»). Движок понимает оба
варианта всегда, независимо от режима.

Секрет webhook: `ROOMS_WEBHOOK_SECRET` — проверяется в заголовке `X-Rooms-Token` (или `Authorization: Bearer`).

Тело ответа webhook содержит сформированные сообщения (`messages`) — пригодится, если Rooms умеет
синхронный ответ на webhook, тогда исходящий вызов API можно не настраивать.

## Как работает диалог (лист «Логика ответов»)

| Ситуация | Что делает бот | Учёт |
|---|---|---|
| Открытие | приветствие один раз за сеанс + главное меню: Типовые вопросы · Инструкции · Чек-листы · Нужна помощь | сеанс |
| Выбор раздела | список тем (до 8); если тем больше — сначала подразделы (Подготовка, Связь и сбои, …), так до любой темы ≤ 3 нажатий | — |
| Выбор темы | опубликованный материал: для чек-листа — «Когда», «Подготовьте», пункты, «Результат», «Если не получается», ссылка на документ | тема, время, версия |
| Повтор темы в сеансе | тот же материал | то же обращение |
| Оценка | «Помогло» → спасибо + Меню; «Не помогло» → «Другие темы» / «Нужна помощь» / Меню | все нажатия в журнале, итоговая — последняя |
| Нужна помощь | три типа обращения → контакт или порядок (`help_routes.yaml`); открытие контакта не подтверждает разговор | тип помощи, тема (если была) |
| Свободный текст, вложение | предлагает меню, по смыслу не отвечает | текст вопроса — в журнал для ответственного (`questions_without_answer`) |
| Ошибка выдачи / неопубликованный материал | сообщение о недоступности, ссылка на документ, помощь; случайный материал не показывается | `material_error` |

Окончание сеанса (открытый вопрос v11) — параметр `SESSION_TTL_MIN`: после N минут тишины следующий
запрос открывает новый сеанс. Поиск по словам (v9) остался за флагом `SEARCH_ENABLED=true`.

## Содержание: как править без разработчика

Каждый материал — запись в `content/cards.yaml` с полями шаблона «Карточка чек-листа»:
`id`, `type` (answer / instruction / checklist), `group`, `title`, `when`, `prepare`, `steps`, `result`,
`help`, `source` (doc / section / link_key или url / version), `owner`, `reviewer`, `version`, `checked`,
`status` (draft / approved / published / retired).

- **Бот выдаёт только `status: published`.** Черновики и снятые версии не показываются, но хранятся в том же
  файле — по одному `id` может быть несколько записей с разными `version`. Опубликованной должна быть ровно
  одна (проверяется при загрузке). Журнал хранит версию показанного материала, поэтому старые версии
  нужны для разбора обращений.
- Обновление текста: добавьте запись с новой `version` и `status: published`, старой поставьте `retired`,
  запустите `python scripts/validate_content.py`, перезапустите бота. CI делает ту же проверку.
- Правила проверки: название ≤ 60 знаков, текст ≤ 600, пунктов ≤ 6, у чек-листа обязателен `result`;
  предупреждения — нет `owner`/`reviewer`/`checked`/`help`/источника, слова «пароль»/«код».
- Импорт из xlsx: `python scripts/import_registry.py "Чек-листы_бота_Rooms_v11.xlsx" --merge` — читает
  каждый заполненный лист по шаблону «Карточка чек-листа» (колонка «Для заполнения») и добавляет/обновляет
  записи по `id`+`version`. Статус берётся из карточки (черновик → `draft`).

Ссылки на документы — `content/params.yaml`; контакты «Нужна помощь» — `content/help_routes.yaml`
(сейчас заглушки «укажите контакт…»).

## Журнал и метрики (п. 6 бизнес-требований, лист «Метрики»)

Таблица `events`: время, сеанс, участник (`user_ref`), событие, тема, версия, оценка, тип помощи, текст вопроса.
Участник пишется как есть (`JOURNAL_USER_MODE=plain`) — он нужен для ручной привязки сеанса к ПИ;
если согласуют обезличивание — `JOURNAL_USER_MODE=hash`. Содержание ПИ не хранится; номер ПИ Аватар не вводит.

- `GET /metrics/summary?since=…&until=…` — выданные ответы (уникальные обращения «сеанс+тема»), охват оценкой,
  полезность (по последней оценке), доля запросов помощи, помощь без темы, темы с «Не помогло»,
  вопросы без ответа. При нулевом знаменателе — `null` («нет данных»).
- `GET /metrics/appeals.csv` — обращения для привязки к ПИ: участник, сеанс, время первого и последнего
  действия, тема, версия, итоговая оценка, помощь.
- `GET /metrics/journal.csv` — сырой журнал; `python scripts/export_journal.py` — то же из консоли.

Если задан `METRICS_TOKEN`, эндпоинты требуют заголовок `X-Metrics-Token`. Использование в ПИ и нагрузка
ревизора считаются вручную по `appeals.csv` и наблюдению, как описано в v11.

## CI (GitLab)

`.gitlab-ci.yml`: проверка содержания → lint (ruff) → тесты (junit-отчёт) → сборка и push образа
в registry проекта на default-ветке и тегах. Переменные проекта: `PIP_INDEX_URL` (зеркало PyPI),
опционально `DOCKER_IMAGE`.
